# __NAME__-remote

Generated by `portal-cli create remote __NAME__`. The code is owned by your team from now on; the template is never
synced again. `portal-cli verify` (in CI) is the permanent consistency check; platform changes that need code edits
reach you as migrations you run yourself (`pnpm upgrade:platform`, see below).

## Run

| Command | What |
|---|---|
| `pnpm dev:standalone` | the remote alone at http://localhost:__PORT__ with a mock platform (mock login, devtools) |
| `pnpm dev` | the same dev server without opening a browser: what the host connects to |
| `pnpm build && pnpm verify` | the release build (`dist/`, `dist-bridge/`) and the integration-contract check, as in CI |
| `pnpm lint`, `pnpm typecheck`, `pnpm test` | the rest of CI |
| `pnpm exec portal-cli add page settings` | a new FSD slice |
| `pnpm upgrade:platform` | bump the `@portal-poc/*` packages, apply their migrations, run the checks (below) |

**Inside the host**: in the host repository's `.env.development.local` add
`PORTAL_REMOTE___UPPER_NAME__=http://localhost:__PORT__/mf-manifest.json`, run `pnpm dev` here and there. Without
`PORTAL_STAND=none` the other remotes come as deployed on that stand (the host dev server reads its `/config.json`).

**Data**: `shared/api/http.ts` exports `http`, an axios instance with this team's settings bound to the host's login
(`@portal-poc/http`). `public/config.json` holds the BFF address and token scopes of every environment. Where
`"fakeBackend": true` (local and dev3 at first) requests are answered by `shared/api/fake-backend.ts`; drop the flag
per environment as the BFF appears. Rules: [`docs/react-and-data.md`](docs/react-and-data.md).

**Page titles and leaving a page** (`@portal-poc/platform-runtime`, the same in every mode):

```tsx
usePageTitle(task.title); // the host shows "<title> · <section> · Portal"

// Ask before leaving while the form is dirty (the host's dialog):
const leave = useLeaveGuard({ when: form.formState.isDirty, message: 'The task is not saved' });
// …or your own dialog: { dialog: 'own' } → render it while leave.state === 'asking', answer leave.leave() / leave.stay()
// (e.g. "Save and leave": await submit(); leave.leave()).
// Refuse leaving while saving: useLeaveGuard({ when: mutation.isPending, lock: true, message: 'Saving…' })
// Saved and navigating away yourself: leave.release() first.
```

**Realtime** (opt-in): `@portal-poc/realtime` opens one socket to your BFF with the host's token, only while a page
subscribes — `useRealtimeEvent(realtime, 'items', () => queryClient.invalidateQueries(...))`. See tasks-remote's
`shared/api/realtime.ts`; another client is fine too, as long as it gets its token from `platform.auth`.

**Preload**: `src/app/exposes/preload.ts` prefetches the data of the page the user is about to open (the host calls
it on hover / focus of a link to us, with the path inside this remote). Add a branch for every route that loads data.

Never call React Router's `useBlocker` (lint error): a router supports one blocker and, inside the host, yours is the
host's router. `src/app/exposes/RemoteBridge.tsx` and `src/app/standalone/main.tsx` already render
`<PlatformLeaveBlocker>` for their own routers.

**Upgrading the platform** — when you decide, on a branch like any change:

```sh
pnpm upgrade:platform              # = pnpm dlx @portal-poc/cli@2 upgrade (fresh CLI): latest @portal-poc/*, install, migrations, checks
git diff                           # review what the migrations changed; do the "manual steps" it printed
pnpm exec portal-cli migrate --check   # after bumping versions by hand: what is left to apply (CI warns about it too)
```

Migrations come with the packages (`<package>/migrations`) and only touch code that uses the changed API; a package
version with nothing to change in your code just installs. `--dry-run` shows the bumps first, `--to
@portal-poc/platform-runtime@2.3.0` stops at a version, `--report upgrade.md` writes a summary for the PR.

**Version**: `package.json` holds the line `develop` builds (snapshots are `<version>-snapshot.<run>+<sha>`); set it
to the release train's next version. Release versions come from `release/X.Y` branches and `vX.Y.Z` tags, not from
this file.

## First steps on GitHub

1. Create the repository in the `portal-poc` organisation and push `main` and `develop`.
2. Platform team: let the repository read the `@portal-poc` packages (each package → Package settings → Manage
   Actions access) and add the secrets `PORTAL_NEXUS_USER`, `PORTAL_NEXUS_PASSWORD`, `PORTAL_REGISTRY_SSH_KEY`.
3. First deploy to each stand: fill in **base-path** (`/__NAME__`) and **scopes** (from `public/config.json`) in the
   Deploy form. They become the remote's registry entry (owned by the host team); later deploys keep them.

## Deploy

Nothing deploys by itself: **Actions → Deploy → Run workflow**, pick the stand and the branch or tag.

| Stand | What you can deploy | What happens |
|---|---|---|
| `dev3` | any branch (`develop`, `feature/…`) | rebuilt and overwritten in place |
| `dev2` | the newest `release/X.Y` or its `vX.Y.Z` tag | immutable version (`X.Y.Z`, or `X.Y.Z-rc.N` from the branch) |
| `dev1` | the pilot line's `release/X.Y` or its tags | same |
| `tst` | — | "Promote" in the registry repository copies what passed `dev1` |

Rollback = deploy the previous tag (the published artifact is reused, nothing is rebuilt).
