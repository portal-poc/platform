# Polyrepo dry run

Claim: the monorepo is only a convenience. Proof: `tools/polyrepo` publishes every platform package to a local
registry (Verdaccio = Nexus stand-in) and builds each app as a separate repository outside the monorepo — no
`workspace:` links, own `.npmrc` and lockfile — then generates a new remote with the **published** CLI.

```sh
pnpm polyrepo:registry      # terminal 1: Verdaccio on :4873 (internal scope local-only, everything else proxied)
pnpm polyrepo:dry-run       # terminal 2: publish → split into ../mfe-poc-polyrepo → check every repo
```

Result:

```
repository        install   typecheck lint      test      build     verify
host              ✔         ✔         ✔         ✔         ✔         ·   (verify is for remotes)
tasks-remote      ✔         ✔         ✔         ✔         ✔         ✔
legacy-remote     ✔         ✔         ✔         ✔         ✔         ✔
reports-remote    ✔         ✔         ✔         ✔         ✔         ✔   (generated by the published @portal-poc/cli)
```

## What the monorepo was hiding (all fixed)

| # | Problem | Why it worked in the monorepo | Fix |
|---|---|---|---|
| 1 | **Dependency confusion**: an unrelated public package `portal-cli@1.0.0` exists on npmjs; generated remotes depended on `portal-cli@^1.0.0` | `workspace:` link | CLI renamed to **`@portal-poc/cli`** (command stays `portal-cli`); every internal package is under `@portal-poc`; generated remotes get an `.npmrc` pinning `@portal-poc:registry` to the internal registry. In Nexus: the internal scope must never be proxied from npmjs |
| 2 | 4 of 7 packages shipped TypeScript sources (`mf-shared`, `vite-config`, `presets` vitest/steiger, CLI); Node refuses to strip types inside `node_modules` | sources resolved through workspace symlinks outside `node_modules` | Every package builds to JS (`tsc`, CLI with `rewriteRelativeImportExtensions`) and publishes `dist` via `publishConfig` |
| 3 | `@types/node` missing for `vite.config.ts` / `vitest.config.ts` | hoisted from the root | Separate `tsconfig.node.json` for build configs (`@portal-poc/presets/tsconfig/build-config.json`) + `@types/node` per app |
| 4 | The published CLI contained live `.oxlintrc.json` / `.fallowrc.json` in its template; oxlint picked them up from `node_modules/@portal-poc/cli/templates` of every app | the template was not inside `node_modules` | Template dotfiles stored as `_oxlintrc.json`, `_fallowrc.json` (like `_gitignore`, `_npmrc`) and renamed on generation |
| 5 | `@portal-poc/vite-config` imported the optional peer `@rolldown/plugin-babel` statically; the React 18 bridge remote (no compiler) did not install it | resolved from the preset's own dev dependencies | Lazy `import()` only when React Compiler is on |
| 6 | Re-publishing the same version: caches served old content, then pnpm refused a tarball whose checksum changed (`ERR_PNPM_TARBALL_INTEGRITY`, flagged as a possible supply-chain attack) | no publishing at all | Never republish a version (Nexus "disable redeploy"); the dry run uses a fresh `1.0.<timestamp>` per run |
| 7 | `pnpm dlx @portal-poc/cli@latest` ran a day-old CLI from pnpm's global dlx cache | — | Pin the exact CLI version in docs/pipelines (or `--dlx-cache-max-age 0`) |
| 8 | `pnpm dlx` from a folder without `.npmrc` asked npmjs for `@portal-poc/cli` | — | Developers pin `@portal-poc:registry` in `~/.npmrc` (onboarding step) |

Also noticed: pnpm 12 asks to approve "agent skills" shipped by `fallow` (`pnpm approve`) — decide the policy for CI.
